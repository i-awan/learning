


SDD Summary – Internal Scanner with Wiz (Periodic and On-Demand Scanning)
This document summarises the Solution Design Diagram (SDD) for integrating an internal scanning tool ('internal scanner') with Wiz for container image and workload security scanning. The design supports both periodic and on-demand scanning, with a strong emphasis on security, network controls, and banking-grade trust boundaries.
1. Architecture Overview
- The internal scanner acts as a policy enforcement and orchestration layer.
- Wiz provides the scanning capability via its SaaS control plane and distributed scanners (Outpost).
- Wiz Outpost is deployed in a bank-owned AWS account and executes scans (data plane).
- Wiz SaaS acts as the control plane and findings repository.
- All communication from on-premises is outbound-only.
2. Trust Zones
On-Prem / Bank Internal Network:
- CI/CD pipelines or users (callers)
- Internal scanner (policy enforcer)
- Enterprise egress controls (proxy, firewall, DNS allowlisting)

AWS (Bank-Owned Trust Zone):
- Wiz Outpost / Sensor responsible for executing scans
- AWS-native network controls (VPC, security groups, egress gateways)

Internet / Wiz SaaS (External Zone):
- Wiz SaaS API (GraphQL/REST)
- Job queue and orchestration
- Centralised findings store
3. Scanning Models
Periodic Scanning:
- Wiz Outpost scans workloads/images on a scheduled basis.
- Findings (CVEs, severity, metadata) are uploaded to Wiz SaaS.
- Results are indexed by image digest with scan timestamps.

On-Demand Scanning:
- Internal scanner submits a scan request to Wiz SaaS.
- Wiz SaaS queues the job and assigns it to the AWS-based Outpost.
- Outpost pulls the image or metadata, performs the scan, and uploads findings.
4. Findings Retrieval and Policy Enforcement
- Internal scanner queries Wiz SaaS for findings using image digest or latest scan reference.
- Scan freshness (staleness) is evaluated based on environment policy (e.g., prod ≤ 24h).
- Results are normalised into PASS / WARN / FAIL decisions.
- Callers experience a single logical request/response, even if multiple Wiz API calls occur internally.
5. Network and Security Considerations
- No inbound connectivity into on-premises is required.
- All traffic from on-prem to Wiz SaaS is outbound-only over HTTPS (TCP 443).
- Egress traffic is restricted using proxies, firewalls, and FQDN allowlists.
- Wiz Outpost communicates outbound to Wiz SaaS; it does not accept inbound connections.
- Secrets (API tokens) are stored in enterprise secrets managers and never exposed in pipelines.
- Least-privilege service identities are used for Wiz API and Outpost access.
- Full audit logging is enabled for egress traffic, scan requests, and policy decisions.
6. Banking and Regulatory Alignment
- Clear separation of trust zones (on-prem, AWS, SaaS).
- Outbound-only connectivity aligns with zero-trust and bank network policies.
- No container images or sensitive data are transferred to Wiz SaaS; only metadata and findings.
- Design supports auditability, traceability, and controlled promotion decisions.
7. Conclusion
This SDD provides a secure, scalable, and regulator-friendly integration between internal scanning processes and Wiz. By combining periodic and on-demand scanning, enforcing strict network controls, and preserving existing pipeline interfaces, the design enables adoption of Wiz without disrupting established CI/CD workflows.


Disclaimer: Placement of Wiz Outpost in AWS vs On-Premises

Note: While the Solution Design Diagram illustrates an option where Wiz Outpost is deployed in a bank-owned AWS account, this deployment model is not the preferred option for a regulated banking environment. The recommended and preferred deployment model is to host Wiz Outpost on-premises, within the bank’s internal Kubernetes environment.

Rationale for Preference of On-Prem Deployment
1. Network Security and Trust Boundaries

In a banking environment, on-premises and cloud environments are treated as separate trust zones, even when the cloud account is fully bank-owned.

Deploying Wiz Outpost in AWS introduces a requirement for cross-zone access between AWS and on-prem resources (e.g. image registries or workloads), which:

Expands the attack surface

Increases firewall and routing complexity

Requires additional network security exceptions

An on-prem Outpost allows all sensitive interactions (image access, runtime inspection) to remain entirely within the internal trust boundary, with outbound-only connectivity to Wiz SaaS.

2. Inbound Connectivity Avoidance

Banking network policy typically disallows inbound connectivity into on-prem environments, including connections initiated from cloud platforms.

An AWS-hosted Outpost scanning on-prem images may require:

Inbound firewall rules

Bi-directional network paths (VPN / Direct Connect)

An on-prem Outpost avoids this entirely by:

Initiating all connections outbound

Aligning with zero-trust and default-deny network postures

3. Data Residency and Exposure Minimisation

Although Wiz does not exfiltrate image data to SaaS, deploying Outpost in AWS can still:

Increase perceived data exposure

Trigger additional regulatory scrutiny around cross-environment data movement

Hosting Outpost on-prem ensures:

Image layers and runtime metadata never leave the data centre

Only vulnerability metadata (CVEs, severity, timestamps) is transmitted externally

4. Performance and Latency Considerations

Scanning images from on-prem registries (e.g. Nexus) via an AWS-hosted Outpost introduces:

Additional network hops

Dependency on WAN/Direct Connect performance

An on-prem Outpost provides:

Lower latency access to registries and nodes

Faster scan execution

More predictable performance characteristics

5. Operational Simplicity

An on-prem deployment:

Simplifies network design

Reduces the number of environments requiring security approval

Minimises operational dependencies between infrastructure teams

AWS-based deployment typically requires coordination across:

Cloud security

Network

Platform

On-prem infrastructure teams

6. Regulatory and Audit Posture

Auditors and regulators generally favour designs where:

Security tooling runs as close as possible to the workloads being inspected

Cross-environment dependencies are minimised

An on-prem Outpost deployment is easier to:

Explain

Justify

Evidence during audits

Summary Position

While deploying Wiz Outpost in a bank-owned AWS account is technically feasible, it is considered a non-preferred implementation option. For security, network simplicity, performance predictability, and regulatory alignment, the preferred deployment model is to host Wiz Outpost on-premises, within the same environment as the workloads and registries being scanned, using outbound-only connectivity to Wiz SaaS.



While deploying Wiz Outpost in a bank-owned AWS account is technically feasible, an on-premises deployment is generally preferred in a banking environment. Hosting Outpost on-prem keeps image access and scanning local to the source registries and workloads, avoiding unnecessary cross-environment data movement and potential bandwidth overhead associated with copying image layers over WAN or Direct Connect links. From a security perspective, an on-prem deployment better aligns with established trust boundaries and default-deny network postures by requiring only outbound connectivity to Wiz SaaS, reducing complexity and minimising exposure introduced by cross-zone dependencies
