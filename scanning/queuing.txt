--------------------------------------------------------------------------------
1. CONTEXT & PROBLEM STATEMENT
--------------------------------------------------------------------------------

The Scanner Handler acts as an abstraction layer between internal CI/CD pipelines
and Wiz's image scanning capability. With thousands of scan requests per day
arriving in burst patterns from CI/CD pipelines, the architecture must be
validated against Wiz's actual capacity characteristics — both for cloud images
(Wiz SaaS) and on-prem images (Outpost Lite).

The core concern is that Wiz's internal queuing and throughput limits are largely
undocumented from the integration side, creating architectural risk.

NOTE: The Scanner Handler currently runs on a VM with planned migration to GKE.
Recommendations in this document address both deployment contexts.


--------------------------------------------------------------------------------
2. TWO SCAN PATHS — DIFFERENT PROBLEMS
--------------------------------------------------------------------------------

There are two distinct scanning paths, each with fundamentally different queuing
characteristics and risk profiles.

  PATH  IMAGE TYPE                SCANNER                  QUEUING MODEL
  ----  ------------------------  -----------------------  --------------------------------
  1     Cloud images (ECR)        Wiz SaaS                 Wiz internal — auto-scaling,
                                                           undocumented limits
  2     On-prem / cluster images  Outpost Lite             No queue — Kubernetes pod
                                  (K8s daemonset)          scheduling is the queue

5. SCANNER HANDLER MITIGATIONS
--------------------------------------------------------------------------------

Regardless of what Wiz's actual limits are, the following mitigations can be
implemented on the Scanner Handler side to protect against being flooded beyond
its capacity to forward requests.


5a. Current State — VM Deployment
-----------------------------------

  RISK: A VM-based Scanner Handler has no autoscaling. A burst of requests that
  exceeds the VM's capacity will either queue in memory (lost on restart) or drop
  connections. There is no backpressure mechanism.

  MITIGATION                        DETAIL                                              APPLIES TO
  --------------------------------  --------------------------------------------------  -----------
  Concurrency limit on API layer    Enforce max concurrent requests (e.g. 100) at the   VM + GKE
                                    web server level. Return 429 with Retry-After
                                    header when exceeded. Callers back off rather
                                    than overloading the VM.

  Rate-limited drainer to Wiz       Token bucket controlling submissions to Wiz.         VM + GKE
                                    Tuned to Wiz tenant rate limit. Prevents 429
                                    cascade from Wiz back to Scanner Handler.

  Pub/Sub as durable ingestion      Accept request, write to Firestore, publish to       VM + GKE
  buffer                            Pub/Sub, return 202 immediately. Queue absorbs
                                    burst; drainer processes at safe rate. Jobs
                                    survive VM restart.

  Concurrency gate for Outpost      Cap the number of simultaneous scan pods             VM + GKE
  Lite                              submitted to the cluster. Excess jobs wait in
                                    Pub/Sub, not as Pending pods. Prevents cluster
                                    saturation.

  Reconciler CronJob                Detects jobs stuck in PENDING beyond threshold       VM + GKE
                                    and requeues them. Safety net for publish
                                    failures or pod crashes mid-submission.

  Circuit breaker on Wiz API        If Wiz returns 5xx or 429 consecutively beyond      VM + GKE
  calls                             threshold, open the circuit. Stop submitting
                                    for a backoff window. Prevents thundering herd
                                    on Wiz recovery.


5b. Target State — GKE Deployment
------------------------------------

GKE unlocks additional mitigations not available on a VM:

  GKE CAPABILITY                    HOW IT HELPS
  --------------------------------  -------------------------------------------------------
  Horizontal Pod Autoscaler (HPA)   Scale worker pods based on Pub/Sub undelivered message
                                    count. Burst traffic spins up more workers automatically;
                                    idle periods scale back to minimum.

  Pod Disruption Budget             Ensures minimum scanner handler pods remain available
                                    during node maintenance or rolling deployments. Prevents
                                    accidental total outage.

  Liveness + Readiness Probes       Unhealthy pods removed from load balancer immediately.
                                    Kubernetes restarts stuck or deadlocked pods automatically.

  Dedicated node pool for scan      Isolates Scanner Handler resource consumption from other
  workers                           workloads. Burst scanning does not degrade unrelated
                                    services.

  Resource requests and limits      Prevents any single pod consuming disproportionate
                                    memory/CPU. OOM kills are bounded and predictable.
